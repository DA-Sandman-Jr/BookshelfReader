# B44 Tooling Traps

This file is generated from canonical `B44.Standards` guidance. Change the source in the B44.Standards repository rather than editing a consumer's generated copy.

## Formatting and analyzers

- A `dotnet format --verify-no-changes` validation run is different from an automated fixer run. For fixes, use `dotnet format whitespace <solution>` plus narrowly targeted `dotnet format style <solution> --severity info --diagnostics <known-fixable IDs>` invocations.
- Do not put `IDE0130` or `MA0051` in a fixer diagnostic list. Their current fix paths are unsupported; repair namespace/folder mismatches and overlong methods deliberately by hand.
- Analyzer severities belong only in B44.Standards' packaged globalconfig. A repository `.editorconfig` outranks global configs and can create an unresolvable policy conflict.
- On Windows with `core.autocrlf=true` and no `.gitattributes`, `dotnet format --verify-no-changes` reports a mass of `ENDOFLINE` errors that do not exist in the committed blobs or in CI. Working files are CRLF, committed content is LF, and the editorconfig wants LF. Do NOT "fix" these by rewriting line endings — that is a repository-wide diff that hides the real change. To check formatting honestly, verify against an LF checkout: `git -c core.autocrlf=false worktree add <tmp> HEAD`, apply the change there with `git -c core.autocrlf=false apply`, and run the format check inside that worktree. Both `git apply` and `git checkout` re-apply autocrlf unless told otherwise, so the flag is needed on each.
- **Never filter that output down to a list of error categories you expect.** Doing so silently removes coverage for every category outside the filter. In an LF worktree the assertion is the command's own exit code — it is already non-zero if any file would change:

  ```bash
  dotnet format --verify-no-changes
  ```

- **Do not pipe that command into `grep` to decide pass/fail.** A pipeline reports the exit status of its *last* command, so `... 2>&1 | grep -cE "error "` throws the real verdict away and substitutes `grep`'s, which is backwards: `grep` exits 0 when it finds a match. The pipeline therefore "passes" exactly when there are violations and "fails" on a clean tree. Pipe only when you want to read or count the diagnostics, and keep that separate from the assertion:

  ```bash
  dotnet format --verify-no-changes > format.log 2>&1   # assertion: this command's exit code
  grep -cE "error " format.log                          # triage only, after the assertion
  ```

  Redirect rather than pipe: a redirection preserves the command's exit status, a pipe replaces it. (`set -o pipefail` also works in bash, but it is easy to forget and absent in plain `sh`.)

  Filtering by category is only ever valid in a CRLF working tree, where it is a triage aid and not a verification — a "clean" result there proves nothing about the categories you filtered out.

## Build isolation

- Concurrent repositories can cross-talk through reused MSBuild nodes and the shared compiler server on this machine. Run build and test verification with `/nodeReuse:false -p:UseSharedCompilation=false -m:1` so another repository's diagnostics cannot contaminate the result.

## Baselines, text, and packages

- Before measuring a clean baseline, remove only the intended repository's resolved `bin` and `obj` directories. Build products survive checkout and reset and can fake the result.
- **Measure an analyzer bump against every consumer before publishing it.** A
  clean package build does not represent consumers that enable stricter rules.
  Add the candidate version as a temporary direct `PackageReference`, rebuild
  each consumer, and record the diagnostic delta. Enforcement-expanding changes
  still require a minor version boundary; measurement establishes the migration
  cost.
- **After changing an analyzer package version, verify with `-t:Rebuild`.** MSBuild does not re-run analyzers on a project whose own inputs have not changed, and changing only the analyzer dependency may leave application outputs considered current. An ordinary incremental build can therefore omit diagnostics that a clean checkout reports.
- Preserve each edited file's existing encoding, BOM, final newline, and line-ending style. Do not let a bulk text-mode rewrite silently normalize unrelated lines.
- Immediately after publishing a new package version, use `dotnet restore --no-cache` in its first consumer validation so a stale local HTTP index cannot masquerade as the new package being absent.
- **`--no-cache` on `restore` is not enough, because `dotnet build` runs its own implicit restore that does not inherit the flag.** After a clean restore, pass `--no-restore` to the build or clear the HTTP cache explicitly with `dotnet nuget locals http-cache --clear`.
